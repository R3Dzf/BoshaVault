# Local Wi-Fi transfer

Use stable Windows 1.12.0 and Android 1.8.0 or newer. Both devices must share a reachable local Wi-Fi network or hotspot; internet access and cloud login are unnecessary. Guest/client-isolated networks cannot carry direct phone-to-PC traffic.

On Windows unlock the vault, open **Devices & encrypted backup**, choose the physical Wi-Fi IPv4 from the interface list and start a new transfer. Keep the window open. On Android choose **Connect to Windows over Wi-Fi**, scan the current QR and press **Connect & transfer**. Complete any local passphrase prompt within the three-minute countdown. Closing, locking or backgrounding cancels the transfer. A failed return upload leaves the phone's merged vault intact; retry with a new Windows session if needed.

Windows' optional private-Wi-Fi helper requests UAC approval and creates/updates exactly one rule for the current installed executable, inbound TCP, Private profile, LocalSubnet peers and blocked edge traversal. It neither changes network profiles nor disables the firewall. Set your trusted home network to Private yourself. A rule for an old ZIP executable path does not cover the newly installed executable. The helper is packaged with both the ZIP and Velopack installation.

Android binds each transfer socket to an eligible Wi-Fi Network before connecting, including Wi-Fi without INTERNET or VALIDATED capabilities. It does not bind the whole process or use a cellular/VPN Network as a substitute. A phone-hosted hotspot without a Wi-Fi Network handle uses its WLAN/AP source IPv4 only if the PC is on the same subnet; actual OEM hotspot routing still needs device acceptance.

The Windows listener binds one selected private IPv4. Up to four clients can negotiate concurrently, with a 12-second TLS/header bound and serialized authenticated vault operations. Three download attempts share one encrypted snapshot. A successfully merged upload has a ten-second receipt window, bounded by the original expiry: the exact SHA-256-matching encrypted body can recover its acknowledgement without a second merge; a different upload and all further downloads are rejected. Android retries transport interruptions up to three times. Upload retries require the server's `X-Lockvyn-Transfer: 2` advertisement; older servers receive a single upload attempt. TLS certificate failures and HTTP rejection are not retried. No pin, token, payload or passphrase is logged.

Acceptance includes real Windows Schannel/private-address TLS lifecycle tests, stalled sockets, bounded download retries, lost acknowledgements, different-upload rejection and diagnostic redaction. Native emulator acceptance routes an Android socket through its Wi-Fi Network to the real .NET endpoint, checks certificate/token rejection, injects transport interruptions to check fresh-socket GET/POST retries and the three-attempt bound, opens the encrypted Windows vault locally, returns an encrypted edit and verifies the edit in .NET. Native routing-policy tests include unvalidated/offline Wi-Fi and reject cellular/VPN transport. CI also performs in-place Windows/Android upgrade preservation checks. Physical phone/PC network and router/firewall behavior must still be checked on the actual devices.
